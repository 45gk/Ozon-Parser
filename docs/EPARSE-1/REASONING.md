# Журнал решений: как я шёл к рабочему парсеру Ozon

> **Важно.** Это не дословный внутренний chain-of-thought — такого готового текста у меня нет, и сырой поток мыслей всё равно плохо учит. Ниже — восстановленный журнал: какие факты я видел, какие гипотезы проверял, что отбросил, где ошибся и почему менял курс. Для обучения это честнее и полезнее, чем «красивая» финальная логика задним числом.

---

## 0. Как читать этот файл

Держи три уровня раздельно:

- **Факт** — что реально наблюдалось (HTTP-код, заголовок страницы, поле JSON).
- **Гипотеза** — объяснение, которое ещё не доказано.
- **Решение** — что я сделал после проверки.

Главный навык здесь не «знать Playwright», а уметь быстро отличать факт от гипотезы и ставить эксперимент, который их разделяет.

### 0.1. Пять вопросов, которые я задаю до кода

1. **Что именно болит?** Не «сделай парсер», а «какое поле/сценарий сейчас недоступен».
2. **Какой минимальный факт я могу проверить прямо сейчас?** Не «работает ли API вообще», а «что вернёт один конкретный запрос».
3. **Какие 2–3 гипотезы объясняют failure?** Если гипотеза одна, я, скорее всего, уже в неё влюбился.
4. **Какой самый дешёвый эксперимент различит гипотезы?** Один `curl`, один `page.title()`, один `navigator.webdriver`.
5. **Что я сознательно не буду делать?** (обходить защиту, менять 10 переменных сразу, хардкодить один ответ).

Эти вопросы занимают меньше времени, чем рефакторинг после неверной гипотезы.

## 1. Что на самом деле просили

Буквально: «я нашёл API-роут, вот пример JSON, давай получать данные оттуда».

За этим стояло несколько задач:

1. **Понять формат.** Ozon отдаёт не «плоский JSON товара», а `layout` + `widgetStates`, где каждый виджет — отдельная JSON-строка.
2. **Встроить API в существующий проект.** Уже был HTML-парсер на JSON-LD/Open Graph, CLI и модель `OzonProduct`. Ломать это не хотелось.
3. **Получить живые данные, а не только разобрать файл.** Иначе это был бы не парсер, а «читалка одного сохранённого ответа».
4. **Не уйти в обход защиты.** В README проекта уже было заявлено: парсер не пытается обходить ограничения. Это ограничение я воспринял как требование, а не как формальность.

Ключевая развилка, которую я сформулировал для себя так:

> «Можно ли получить данные из этого источника?» и «Можно ли делать это автоматически из Python?» — это два разных вопроса. Первый решается парсингом JSON, второй упирается в антибот.

## 2. Разведка перед кодом

### 2.1. Что лежало в проекте

```
ozon-parser/
├── json_responce.json   # 275 КБ, пример ответа
├── ozon_parser/
│   ├── parser.py        # OzonProduct + JSON-LD/Open Graph
│   ├── fetch.py         # HTML-загрузчик
│   └── cli.py           # ozon-parse URL
├── app/                 # пустая папка
├── pyproject.toml
└── README.md
```

Выводы:

- проект маленький, без FastAPI и БД;
- зависимости минимальные (`httpx`);
- тестов нет;
- HTML-парсер уже умеет доставать базовые поля, значит модель `OzonProduct` можно переиспользовать.

### 2.2. Что было в `json_responce.json`

Файл оказался не одним чистым JSON, а объектом с двумя backtick-ами в конце — след копирования из DevTools. Это сразу стало требованием к парсеру: **не падать на артефактах копирования**.

Верхний уровень:

```text
layout, widgetStates, browser, client, seo, pageInfo,
pageToken, requestID, verticalInfo, resolveParams, ...
```

`widgetStates` — 82 записи. Значения — **JSON-строки**, а не объекты. Пример:

```json
"webPrice-3121879-default-1": "{\"isAvailable\":true,\"cardPrice\":\"236 ₽\",...}"
```

Отсюда родилось правило: декодировать состояние один раз, а не при каждом обращении.

### 2.3. Что дала картинка из DevTools

На скриншоте был виден запрос:

```text
GET https://www.ozon.ru/api/entrypoint-api.bx/page/json/v2?url=%2Fproduct%2F...%3Fat%3D...%26sh%3D...
200 OK (from service worker)
```

Два важных наблюдения:

1. **Это действительно GET с параметром `url`**, а не POST с телом. Значит, URL можно собрать детерминированно.
2. **`from service worker`** — ответ мог быть отдан из кэша service worker, а не из сети. Это позже объяснило, почему «в браузере работает, а из Python — нет»: браузерный контекст и кэш — часть уравнения.

## 3. Как я построил модель данных

Я не стал парсить «как получится». Сначала составил таблицу «виджет → поле»:

| Виджет | Поле |
|---|---|
| `webProductHeading.title` | `name` |
| `webPrice.price` | `price` |
| `webPrice.cardPrice` | `card_price` |
| `webPrice.originalPrice` | `original_price` |
| `webPrice.isAvailable` | `in_stock` |
| `webReviewProductScore.totalScore` | `rating` |
| `webReviewProductScore.reviewsCount` | `review_count` |
| `webGallery.images[].src` | `image_urls` |
| `webDetailSKU.copyText` / `webProductMainWidget.sku` / `pageInfo.analyticsInfo.sku` | `sku` |
| `webShortCharacteristics.characteristics` | `characteristics` |
| `webCurrentSeller.sellerCell.centerBlock.title` / `webStickyProducts.seller.name` | `seller` |
| `webDescription.text` | `description` (если есть) |
| `webBrand.title` | `brand` (если есть) |
| `seo.link[rel=canonical]` | `source_url` (fallback) |

### 3.1. Почему поиск по префиксу, а не по точному ключу

Ключи выглядят так:

```text
webPrice-3121879-default-1
webGallery-3311626-default-1
```

Числа и суффиксы меняются от карточки к карточке. Поэтому функция `_state(states, "webPrice")` ищет `key == prefix` или `key.startswith(prefix + "-")`. Это устойчивее, чем хардкод конкретного stateId.

### 3.2. Почему несколько fallback-ов на одно поле

У Ozon нет одного стабильного источника истины:

- SKU есть в `webDetailSKU`, `webProductMainWidget`, `webGallery`, `pageInfo`;
- имя — в `webProductHeading` и `webStickyProducts`;
- продавец — в `webCurrentSeller` и `webStickyProducts`.

Если брать только один виджет, парсер будет ломаться на каждой второй карточке. Fallback — это дешёвая страховка.

### 3.3. Цены: самая неприятная семантика

В ответе одновременно:

```text
price: 251 ₽
cardPrice: 236 ₽
originalPrice: 999 ₽
```

Что считать «ценой»? Варианты:

- `236` — то, что видит покупатель с Ozon Картой;
- `251` — обычная цена;
- `999` — зачёркнутая.

Я выбрал:

- `price` = обычная цена (`251`);
- `card_price` = цена с картой (`236`);
- `original_price` = до скидки (`999`).

Причина: «цена» не должна молча зависеть от наличия карты. Лучше отдать все три поля и явно назвать их, чем прятать условие в одном числе.

### 3.4. Чего в ответе не было

`description` и `brand` отсутствовали: виджетов `webDescription` и `webBrand` в этом ответе нет. Я не стал подменять описание SEO-метатегом («покупайте на OZON...») — это не описание товара, а маркетинговый текст. Лучше `null`, чем правдоподобная неправда.

## 4. Проектные решения

### 4.1. Отдельный `api.py`

Можно было дописать всё в `parser.py`, но тогда смешались бы:

- HTML-парсинг;
- JSON-парсинг;
- сборка URL;
- HTTP-запрос;
- антибот-ошибки.

Вынес API в отдельный модуль. `parser.py` остался про HTML и модель, `api.py` — про `entrypoint-api`, `browser.py` — про браузер. Это позволяет тестировать слои независимо.

### 4.2. Расширение dataclass в конец

`OzonProduct` — frozen dataclass. Новые поля добавил **в конец**, с дефолтами:

```text
original_price, card_price, in_stock, seller, brand, characteristics
```

Так старый позиционный вызов не ломается, а `to_dict()` продолжает отдавать стабильный JSON.

### 4.3. Ошибки как часть UX

Плохая ошибка: `HTTP 403`.
Хорошая ошибка говорит:

- что случилось;
- почему;
- что делать дальше.

Примеры:

```text
Ozon отклонил запрос к API (HTTP 403, антибот-защита).
Сохрани ответ entrypoint-api из DevTools и передай его через --json
или укажи cookie браузера...
```

```text
Ozon показал страницу «Похоже, нет соединения» — это антибот-блок
для автоматизированного браузера, а не проблема сети...
```

Это не «украшательство»: при scraping-задачах 80% времени пользователь проводит в разборе ошибок. Сообщение — часть продукта.

### 4.4. Playwright — опциональная зависимость

Playwright тяжёлый (Python-пакет + браузер). Людям, которым нужен только `--json`, он не нужен. Поэтому:

```toml
[project.optional-dependencies]
browser = ["playwright>=1.50,<2"]
```

И `browser.py` импортирует Playwright в `try/except`. Проверил отдельно: `import ozon_parser` работает без Playwright, а вызов браузерной функции даёт понятную команду установки.

## 5. Эксперименты: что я проверял и что это доказывало

### 5.1. Прямой HTTP

```bash
curl -i 'https://www.ozon.ru/api/entrypoint-api.bx/page/json/v2?url=...'
```

Наблюдение:

```text
HTTP/2 307
location: ...&__rr=1
set-cookie: __Secure-ETC=...
```

С follow-redirects и cookie jar:

```text
HTTP/2 403
{"incidentId": "...", "challengeURL": "https://www.ozon.ru/challenge.html?..."}
```

**Вывод:** это не «неправильный URL» и не «нужен POST». Запрос доходит до антибот-слоя.

### 5.2. Гипотеза «не хватает браузерных заголовков»

Добавил:

```text
User-Agent Chrome
Accept: application/json
Accept-Language: ru-RU
Referer
Origin
Sec-Fetch-*
x-o3-app-name: dweb_client
```

Результат: всё тот же `403` + `challengeURL`.

**Вывод:** дело не только в заголовках. Значит, либо TLS/JS-фингерпринт, либо cookie/сессия, либо комбинация. Менять заголовки дальше — трата времени.

### 5.3. Гипотеза «Playwright всё решит»

Playwright + системный Chrome:

- **headless** → `403`;
- **headed** → `Antibot Challenge Page`, затем «Похоже, нет соединения».

Скриншот показал не капчу, а заглушку:

```text
Похоже, нет соединения
Выключите VPN, перезагрузите роутер или подключитесь к другой сети
```

**Вывод:** Ozon видит именно автоматизированный браузер. Сеть тут ни при чём — обычный Chrome с того же IP открывал карточку.

### 5.4. Гипотеза «дело в профиле/автоматизации»

Проверил в Playwright:

```python
page.evaluate("() => navigator.webdriver")
# True
```

Это важная точка. Playwright запускает Chrome с флагом автоматизации, и сайт может это прочитать. Дальше был выбор:

- добавить stealth-патчи и маскировать автоматизацию;
- не делать этого;
- найти способ использовать **обычный** браузер.

Я выбрал третий путь, потому что он не требует обхода детекта: пусть браузер действительно будет обычным, а Python только подключается к нему.

### 5.5. CDP к вручную запущенному Chrome

Запустил Chrome отдельно:

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --remote-debugging-port=9222 \
  --user-data-dir=/tmp/ozon-cdp-profile
```

Подключился через `playwright.chromium.connect_over_cdp("http://127.0.0.1:9222")`.

Наблюдения:

```text
navigator.webdriver: False
url: .../product/.../?__rr=1
title: Antibot Challenge Page
title через 3 секунды: Биты магнитные, усиленные для шуруповерта купить на OZON...
api: 200
```

**Вывод:** ключевое отличие — не «Playwright vs не Playwright», а **контекст браузера**. Обычный Chrome, запущенный пользователем, проходит проверку; автоматизированный — нет.

### 5.6. Сводная таблица экспериментов

| Гипотеза | Эксперимент | Результат | Вывод |
|---|---|---|---|
| URL API неверный | curl с параметром `url` | 307 → 403 | URL верный, дело в защите |
| Не хватает заголовков | браузерные заголовки | 403 | заголовки не решают |
| Playwright обойдёт | headless/headed | 403 / заглушка | автоматизация детектится |
| Виновата сеть | обычный Chrome с того же IP | карточка открылась | сеть ни при чём |
| Дело в automation | `navigator.webdriver` | `true` у Playwright | гипотеза подтвердилась |
| Обычный Chrome поможет | CDP к ручному Chrome | `200`, JSON | рабочий путь найден |

## 6. Как я локализовал проблему по слоям

Когда «не работает», полезно не менять всё сразу, а идти по слоям:

```text
1. Сеть/DNS/TLS      → curl доходит? какой HTTP-код?
2. HTTP-ответ         → JSON или HTML? есть incidentId/challengeURL?
3. Браузер           → страница открылась? какой title/url?
4. Контекст браузера  → navigator.webdriver? какие cookie?
5. Запрос из страницы → fetch(api_url) какой status?
6. Парсер             → widgetStates есть? нужные виджеты есть?
```

Мой диагностический скрипт печатал:

```text
page.url
page.title()
navigator.webdriver
имена cookie
статус fetch(api_url)
первые 300 символов ответа
скриншот страницы
```

Именно title `Antibot Challenge Page` и последующий «Похоже, нет соединения» дали больше, чем любой анализ заголовков. **Смотри на то, что реально показывает система, а не на то, что должна показывать по твоей теории.**

## 7. Ошибки, которые я допустил, и как исправил

### 7.1. Неправильный импорт

В `browser.py` сначала было:

```python
from ozon_parser.parser import OzonProduct, parse_product_json
```

Но `parse_product_json` живёт в `api.py`. Импорт упал сразу — хорошо, что тесты и запуск это поймали. Исправил на:

```python
from ozon_parser.api import build_api_url, parse_product_json
from ozon_parser.parser import OzonProduct
```

**Урок:** после перемещения функции между модулями всегда проверяй импорт, а не только «мне кажется, должно работать».

### 7.2. Детект challenge только по URL

Сначала проверял:

```python
if "challenge.html" in page.url: ...
```

Но страница «Похоже, нет соединения» сохраняла URL карточки (`?__rr=1`) и при этом была challenge-страницей. Парсер считал, что проверка пройдена, и выдавал misleading-ошибку «Ozon отклонил запрос даже из браузера».

Исправил: проверять не только URL, но и `page.title()`:

```text
antibot, challenge, нет соединения, доступ ограничен
```

**Урок:** URL — не единственный признак состояния страницы. Заголовок и текст часто врут меньше.

### 7.3. CDP не подключался к Chrome без вкладок

Ошибка:

```text
BrowserType.connect_over_cdp: Protocol error (Browser.setDownloadBehavior):
Browser context management is not supported.
```

Оказалось: Playwright не подключается к браузеру, у которого **ноль page-target'ов**. Исправил: при ошибке делаю `PUT /json/new?about:blank`, создаю вкладку и повторяю подключение.

**Урок:** «Protocol error» не всегда про протокол. Иногда это отсутствие ожидаемого состояния (например, ни одной вкладки).

### 7.4. Шумные логи httpx

При создании вкладки через `httpx.put` в консоль попадало:

```text
HTTP Request: PUT http://127.0.0.1:9222/json/new?about:blank "HTTP/1.1 200 OK"
```

Это ломало читаемость JSON-вывода. Добавил:

```python
logging.getLogger("httpx").setLevel(logging.WARNING)
```

**Урок:** библиотека не должна засорять stdout/stderr пользователя своими INFO-логами.

### 7.5. Сначала слишком общая ошибка браузера

Было:

```text
Ozon отклонил запрос к API даже из браузера.
```

Стало:

```text
Ozon показал страницу «Похоже, нет соединения» — это антибот-блок
для автоматизированного браузера, а не проблема сети...
```

**Урок:** ошибка должна не описывать симптом, а называть слой и следующий шаг.

### 7.6. Относительные импорты и инструменты окружения

В этом окружении относительные импорты неожиданно превратились в абсолютные без пакета (`from .api` → `from api`), из-за чего пакет перестал импортироваться. Я перешёл на явные абсолютные импорты `from ozon_parser...`, которые не зависят от таких переписываний.

**Урок:** если инструмент может переписать код — делай импорты однозначными и проверяй `import` после каждого крупного изменения.

## 8. Принципы, которые реально помогли

### 8.1. Сначала дешёвый эксперимент, потом большой код

Прежде чем писать полноценный браузерный модуль, я сделал 20-строчный скрипт: подключиться, открыть страницу, напечатать title, `navigator.webdriver`, статус `fetch`. Это дало ответ за минуты.

### 8.2. Разделяй «получить данные» и «автоматизировать получение»

- Разбор JSON — детерминированная задача, её можно сделать идеально.
- Живой запрос — борьба с чужой защитой, там нет гарантий.

Смешивать эти две задачи в одном коде — значит делать нестабильным то, что могло быть стабильным.

### 8.3. Используй реальную систему как оракул

Не спрашивай «почему мой код не работает», спроси «чем мой запрос отличается от запроса, который работает». В моём случае отличие было в контексте браузера, а не в URL.

### 8.4. Офлайн-проверка до сети

Парсер на фикстуре можно проверить 18 тестами без Ozon, без сети и без антибота. Это быстрый цикл обратной связи. Сетевые эксперименты — дорогие и нестабильные; их надо минимизировать.

### 8.5. Не обходить защиту, а менять точку входа

Вместо stealth-патчей я использовал **другой легальный вход**: обычный браузер пользователя через CDP. Это не «взлом», а интеграция с тем, что уже работает.

### 8.6. Ошибки — это интерфейс

При scraping-задачах пользователь часто не знает, на каком слое упало. Хорошая ошибка экономит часы. Плохая — заставляет менять заголовки наугад.

### 8.7. Не overfit-ить под один ответ

Один сохранённый JSON — это один снимок. Поэтому:

- поиск виджетов по префиксу;
- несколько fallback-ов;
- `null` вместо выдуманных значений;
- тесты на отсутствующие поля.

## 9. Дерево решений для похожих задач

```text
Нужны данные с сайта
│
├─ Есть официальный API? → использовать его
│
├─ Прямой HTTP отдаёт 200 и данные? → парсить
│
├─ 403 / JS challenge / пустая страница?
│   │
│   ├─ Есть сохранённый ответ (DevTools/HAR)? → парсить офлайн
│   │
│   ├─ Есть реальный браузер пользователя?
│   │   ├─ да → CDP к ручному Chrome
│   │   └─ нет → Playwright (понимая, что автоматизация видна)
│   │
│   └─ Нет → документировать ограничение, не изобретать stealth
│
└─ HTML без API? → JSON-LD / микроданные / DOM
```

## 10. Чек-лист для следующей похожей задачи

1. **Собери факты:** какие URL, какие коды, какие заголовки, что в ответе.
2. **Сохрани пример ответа** и сделай офлайн-парсер до сетевых экспериментов.
3. **Составь таблицу «источник → поле»**, а не парси наугад.
4. **Определи семантику** спорных полей (цена с картой? наличие? регион?).
5. **Проверь самый дешёвый запрос** (`curl`/`httpx`) и зафиксируй результат.
6. **Если блок — не меняй 10 заголовков сразу.** Сначала пойми, какой слой режет.
7. **Сравни с работающим клиентом:** браузер, DevTools, `navigator.webdriver`, cookie.
8. **Сделай ошибки actionable:** что произошло, почему, что делать.
9. **Отдели optional-зависимости** и проверь импорт без них.
10. **Напиши тесты на happy path и на отказ.**
11. **Задокументируй ограничения** — это часть результата, а не поражение.

## 13. Главная мысль

Самое важное решение в этой задаче было не «взять Playwright», а **не пытаться победить антибот кодом**. Нужно было найти точку, где система уже работает легально — обычный браузер пользователя — и подключиться к ней.

Если сформулировать коротко:

> Не борись с защитой. Найди контекст, в котором защита уже пройдена, и используй его.

И вторая мысль:

> Каждое утверждение проверяй smallest possible experiment. Один `navigator.webdriver` дал больше, чем сто попыток «поправить заголовки».
