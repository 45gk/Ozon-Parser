# EPARSE-4 — журнал решений: скилл `task-documentation`

> **Важно.** Это не дословный внутренний chain-of-thought, а восстановленный журнал решений: факты, гипотезы, эксперименты, ошибки и выводы. Он показывает не только финальный результат, но и места, где я сомневался и менял курс.

---

## 0. Как читать

- **Факт** — что реально наблюдалось: вывод команды, содержимое файла, ответ `skill`.
- **Гипотеза** — объяснение, которое ещё не проверено.
- **Решение** — что сделано после проверки.

Главная развилка: **где должен лежать скилл, чтобы DSH его увидел**, и **что именно считать «документацией»** — просто шаблон или исполняемый workflow.

---

## 1. Разбор запроса

Буквально: «давай создадим скилл по созданию документации».

За этим стояло:

1. **Повторить формат EPARSE-1/2/3** — `STATUS.md` + `REASONING.md` в папке задачи.
2. **Сделать это переиспользуемым** — не одноразовый текст, а скилл.
3. **Дать агенту инструкции**, а не только примеры.
4. **По возможности автоматизировать** создание папки и файлов.
5. **Не сломать существующие скиллы и проект.**

Ключевой вопрос:

> Достаточно ли `SKILL.md` с чек-листом, или нужен ещё scaffold-скрипт, чтобы скилл реально экономил время?

---

## 2. Разведка

### 2.1. Формат скиллов

Нашёл в runtime:

```text
/Applications/DeepSeek Harness.app/Contents/Resources/runtime/office-skills/<name>/SKILL.md
```

Frontmatter:

```yaml
---
name: office-pptx
description: Create, read, edit, and validate PowerPoint presentations (.pptx).
---
```

Тело — инструкции, ссылки на `references/`, `scripts/`, `assets/`.

### 2.2. Где DSH ищет скиллы

Из кода `dsh-skill-filesystem`:

```text
<project>/.dsh/skills
<project>/.agents/skills
~/.dsh/skills
~/.agents/skills
custom dirs
```

Проект определяется как ближайший родитель с `.git`; если `.git` нет — текущая
директория.

### 2.3. Где находится текущий проект

Факт:

- session cwd = `/Users/igor/Documents/test_project`;
- `.git` есть только в `/Users/igor/Documents/test_project/ozon-parser`;
- значит, для скиллов project root — `test_project` (нет `.git`), а не `ozon-parser`.

Это стало причиной первой ошибки.

## 3. Архитектурные решения

### 3.1. Название

Варианты:

- `documentation` — слишком общее;
- `task-docs` — коротко, но неоднозначно;
- `task-documentation` — точно описывает формат: документация задачи.

Выбрал `task-documentation`. Имя соответствует regex
`[a-z0-9]+(-[a-z0-9]+)*`, не конфликтует с office-скиллами.

### 3.2. Два документа, а не один

`STATUS.md` и `REASONING.md` отвечают на разные вопросы:

- «Что получилось и как это проверить?»;
- «Почему получилось именно так и где я ошибался?».

Если смешать их, статус становится слишком длинным, а журнал — слишком
операционным. Разделение сохраняет оба полезными.

### 3.3. Шаблоны + скрипт

Можно было ограничиться `SKILL.md` с разделами. Но тогда агент каждый раз
вручную создаёт папку и вспоминает структуру.

Добавил:

- `templates/STATUS.md`, `templates/REASONING.md`;
- `scripts/scaffold_task_docs.py` — создаёт папку, подставляет placeholders,
  отказывается перезаписывать существующее.

Это делает скилл **исполняемым**, а не только описательным.

### 3.4. Язык

`SKILL.md` — на английском, как остальные скиллы; шаблоны — на русском, потому
что текущий проект и артефакты русскоязычные. В инструкции явно сказано:
писать на языке пользователя, шаблоны адаптировать.

### 3.5. Две копии

- каноническая: `ozon-parser/.dsh/skills/task-documentation` (в git проекта);
- рабочая: `test_project/.dsh/skills/task-documentation` (нужна, чтобы DSH
  увидел скилл из текущего cwd).

Минус: две копии нужно синхронизировать. Проверил checksum — идентичны.

## 4. Эксперименты

| Гипотеза | Эксперимент | Наблюдение | Вывод |
|---|---|---|---|
| Скилл в `ozon-parser/.dsh` подхватится | создать и вызвать `skill` | `unknown or no longer available` | project root другой |
| Глобальная установка сработает | `cp` в `~/.dsh/skills` | `Operation not permitted` | sandbox запрещает |
| Workspace-корень подхватится | `cp` в `test_project/.dsh/skills` | скилл загрузился | рабочий путь |
| Scaffold создаёт файлы | запуск в `/tmp` | 2 файла + assets | работает |
| Защита от перезаписи | повторный запуск | exit 1, error | работает |
| Placeholders заменяются | `grep -RE '\{\{(TASK_ID|TITLE|DATE|PROJECT)\}\}'` | пусто | работает |

### 4.1. Фактический вывод загрузки

```text
skill("task-documentation")
→ <skill_content name="task-documentation">
```

После этого каталог доступных скиллов обновился и включил
`task-documentation`.

### 4.2. Фактический вывод scaffold

```text
created docs/EPARSE-4/STATUS.md
created docs/EPARSE-4/REASONING.md
created docs/EPARSE-4/assets/
next: fill the placeholders, add evidence, then verify links and test counts
```

Повторный запуск:

```text
error: ... already exists; refusing to overwrite
exit=1
```

## 5. Ошибки и исправления

### 5.1. Скилл не находился

Сначала создал:

```text
ozon-parser/.dsh/skills/task-documentation
```

`skill("task-documentation")` вернул:

```text
unknown or no longer available
```

Причина: session cwd — `test_project`, а project root для сканирования — тоже
`test_project` (там нет `.git`). Вложенная папка `ozon-parser/.dsh` не
сканируется, потому что discovery смотрит только direct entries корня.

Исправление: скопировал скилл в:

```text
test_project/.dsh/skills/task-documentation
```

Скилл загрузился.

**Урок:** сначала выясни, от какой директории считается project root, и только
потом создавай `.dsh/skills`.

### 5.2. Глобальная установка заблокирована

Попытка:

```bash
mkdir -p ~/.dsh/skills
```

Результат:

```text
mkdir: /Users/igor/.dsh/skills: Operation not permitted
```

Это ограничение sandbox, а не ошибка скилла. Записал в ограничения: для
глобальной установки пользователь копирует папку сам.

### 5.3. Дублирование

Появились две копии. Проверил `shasum` — идентичны. В статусе отметил, что при
изменениях их нужно синхронизировать. В следующей итерации можно заменить
workspace-копию симлинком, но это требует проверки, что loader следует
симлинкам.

## 6. Принципы, которые помогли

### 6.1. Скилл должен быть исполняемым

Инструкция «создай папку» — это совет. Скрипт, который создаёт папку и
проверяет overwrite, — это инструмент. Второе полезнее.

### 6.2. Шаблон задаёт качество

Без шаблона каждый STATUS выглядит по-разному. Шаблон с таблицей сценариев,
handoff и definition of done поднимает нижнюю планку.

### 6.3. Реконструкция, а не «сырой CoT»

Скилл явно запрещает выдавать восстановленный журнал за дословные мысли.
Это честнее и полезнее: видны эксперименты и ошибки, а не только финальная
логика.

### 6.4. Один task — одна папка

Это делает артефакты сравнимыми и не даёт перезаписать предыдущий результат.
Скрипт падает, если папка уже есть.

### 6.5. Evidence-first

Скилл требует команды, тесты, живые значения и скриншоты. Без этого документ
превращается в маркетинг.

## 7. Что бы я сделал иначе

- **Сразу проверил бы project root** через тестовый скилл, а не создавал
  вложенную папку.
- **Сделал бы symlink** вместо второй копии, если loader его поддерживает.
- **Добавил бы пример заполненного STATUS/REASONING** в `references/` — это
  ускорило бы адаптацию.
- **Добавил бы проверку ссылок** в scaffold-скрипт.
- **Сделал бы английские шаблоны** для переносимости.

---

## 8. Чек-лист для похожего скилла

1. Определи project root и root скиллов.
2. Проверь формат `SKILL.md` и frontmatter.
3. Сделай имя по regex и без конфликтов.
4. Напиши non-negotiables (что нельзя делать).
5. Дай шаблоны, а не только текст.
6. Добавь scaffold-скрипт с защитой от overwrite.
7. Проверь загрузку через `skill`.
8. Проверь скрипт в отдельной temp-папке.
9. Проверь отсутствие placeholders.
10. Задокументируй ограничения и способ установки.

---

## 9. Упражнения

1. Запусти скилл на следующей задаче и заполни STATUS/REASONING.
2. Добавь пример заполненного документа в `references/`.
3. Сделай английскую версию шаблонов.
4. Добавь в scaffold проверку, что `docs/<ID>` внутри docs root.
5. Попробуй заменить workspace-копию симлинком и проверь discovery.
6. Добавь шаблон постмортема для инцидентов.
7. Сделай `--dry-run` для scaffold.
8. Добавь проверку ссылок на assets.

---

## 10. Главная мысль

Скилл — это не «текст с советами», а **упакованный workflow**:

```text
правила → шаблоны → скрипт → проверка
```

Если убрать любой слой, качество документации становится случайным.
