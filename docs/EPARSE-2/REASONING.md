# EPARSE-2 — журнал решений: как строилось веб-приложение

> **Важно.** Это не дословный внутренний chain-of-thought, а восстановленный журнал решений: факты, гипотезы, эксперименты, ошибки и выводы. Для обучения он полезнее «гладкой» финальной логики, потому что показывает, где я сомневался и что менял.

---

## 0. Как читать

Три уровня:

- **Факт** — что реально произошло (код ответа, лог, скриншот, результат теста).
- **Гипотеза** — объяснение, которое ещё не проверено.
- **Решение** — что сделано после проверки.

Главный вопрос этой задачи был не «как написать FastAPI», а **как разделить приложение и браузер так, чтобы CDP продолжал работать**.

---

## 1. Разбор запроса

Буквально: «сделай FastAPI-приложение с веб-интерфейсом, запускай парсер, смотри результаты и историю; PostgreSQL в Docker; задокументируй как в прошлый раз в папке».

За этим стояло:

1. **Не сломать парсер.** `ozon_parser` — уже рабочая библиотека с CLI. Веб-приложение должно её использовать, а не дублировать.
2. **История — не просто лог.** Нужны статусы, фильтры, поиск, детали, статистика.
3. **Живой Ozon.** Прямой API блокируется; рабочий режим — CDP к обычному Chrome. Значит, веб-приложение должно уметь запускать именно его.
4. **PostgreSQL в Docker.** Но приложение с CDP, скорее всего, должно работать на хосте.
5. **Артефакты.** Отдельная папка `docs/EPARSE-2/` со статусом и журналом решений.

Ключевая развилка:

> «Где запускать веб-приложение?» — если в Docker, оно не увидит Chrome на хосте. Если на хосте, CDP работает, но PostgreSQL можно оставить в Docker.

## 3. Архитектурные решения

### 3.1. Расширять `ozon-parser`, а не делать новый проект

Альтернатива: отдельный репозиторий `ozon-web` с зависимостью на пакет.

Почему расширил:

- парсер и веб-приложение живут в одном контексте;
- одна команда `uv sync` / один Dockerfile;
- проще переиспользовать `OzonProduct` и ошибки;
- пользователю не нужно публиковать пакет, чтобы запустить UI.

Минус: пакет становится тяжелее (FastAPI, SQLAlchemy, Jinja2). Для локального инструмента это приемлемо; для библиотеки можно было бы вынести веб-слой в отдельный extra.

### 3.2. FastAPI + Jinja2 + vanilla JS, а не React

Альтернативы:

| Вариант | Плюсы | Минусы |
|---|---|---|
| Jinja2 + JS | минимум зависимостей, быстрый старт, SEO не важен | нет компонентности |
| React/Vite | богатый UI | сборка, node_modules, два процесса |
| HTMX | простое обновление | ещё одна зависимость, меньше контроля |

Выбрал Jinja2: приложение локальное, экранов мало, а вся динамика — форма и polling. SPA здесь добавила бы сложности без пользы.

### 3.3. Приложение локально, PostgreSQL в Docker

Это главное решение.

Если запустить всё в Docker:

- контейнер обращается к `host.docker.internal:9222`;
- Chrome по умолчанию слушает `127.0.0.1:9222`;
- из контейнера этот порт обычно недоступен;
- можно запустить Chrome с `--remote-debugging-address=0.0.0.0`, но это расширяет поверхность атаки.

Поэтому основной сценарий:

```text
PostgreSQL → Docker
FastAPI     → локально (uvicorn)
Chrome CDP  → локально
```

Полный Docker остаётся для истории/API/HTML и для тех, кто готов настраивать сеть отдельно.

### 3.4. Синхронный SQLAlchemy, а не async

Почему:

- парсер синхронный (httpx, Playwright sync API);
- фоновая задача всё равно выполняется в отдельном потоке;
- sync-сессии проще и меньше шансов смешать event loop и Playwright;
- для локального приложения с одним пользователем производительность не критична.

Минус: sync-роуты FastAPI выполняются в threadpool. Для текущей нагрузки это нормально.

### 3.5. Одна таблица `parse_runs`, а не `products` + `runs`

Альтернатива: нормализовать товары и хранить историю цен отдельно.

Почему одна таблица:

- MVP, одна сущность — один запуск;
- полный JSON уже в `product` (JSONB);
- денормализованные поля нужны только для таблицы истории и фильтров;
- меньше join-ов и кода.

Минус: дублирование данных между `product` и колонками. Это осознанный компромисс; при росте функционала можно выделить `products` и `price_snapshots`.

### 3.6. BackgroundTasks, а не Celery/RQ

Почему:

- один процесс, один пользователь;
- не нужен Redis/брокер;
- статус хранится в БД, UI опрашивает API;
- `threading.Lock` сериализует парсинги.

Минусы:

- очередь живёт в памяти;
- рестарт сервера теряет `queued/running` (помечаем `failed`);
- несколько worker'ов не поддерживаются.

Это записано в ограничениях, а не спрятано.

### 3.7. `create_all`, а не Alembic

Для MVP схема создаётся при старте. Alembic — следующий шаг. Если бы проект сразу шёл в прод, я бы сделал Alembic с первой миграцией и не полагался на `create_all`.

## 4. Модель данных: что важнее

При проектировании `parse_runs` были варианты:

1. хранить только `product` JSONB;
2. хранить только колонки;
3. хранить и то, и другое.

Выбрал третий:

- **JSONB** — полный результат, его можно показать как есть и не терять новые поля парсера;
- **колонки** — быстрые фильтры/сортировки/статистика без запросов внутрь JSON;
- **`options`** — параметры запуска, чтобы понимать, откуда взялся результат.

Что специально **не** храню:

- cookie;
- содержимое профиля браузера;
- пароли/секреты.

`options` содержит только `cdp_url`, таймауты и `headless`.

## 5. Поток выполнения

```text
POST /api/runs
  │
  ├─ Pydantic валидирует URL и параметры
  ├─ RunRepository.create(status="queued")
  ├─ BackgroundTasks.add_task(run_parse, id)
  └─ 202 {id, status}
          │
          ▼
run_parse(id)
  ├─ lock (один парсинг за раз)
  ├─ status = "running", started_at
  ├─ _parse_product(run)
  │    ├─ cdp     → fetch_product_browser(cdp_url=...)
  │    ├─ browser → fetch_product_browser(headless=...)
  │    ├─ api     → fetch_product_api(cookie=env)
  │    └─ html    → fetch_product()
  ├─ success → product JSON + колонки + duration
  └─ error   → status="failed" + текст
```

Почему статус `running` коммитится **до** парсинга: иначе UI не увидит прогресс и будет думать, что задача всё ещё в очереди.

Почему отдельная сессия в `run_parse`: request-scoped сессия закрывается после ответа, а фоновая задача живёт дольше.

Почему `threading.Lock`: Ozon не любит параллельные запросы, а CDP-вкладки проще водить по одной.

## 6. UI: что и почему

### 6.1. Один экран + детальная страница

Дашборд:

- hero с объяснением;
- 5 карточек статистики;
- форма запуска;
- история с фильтрами.

Детальная:

- шапка со статусом и кнопкой «Повторить»;
- мета-строка;
- карточка товара;
- характеристики;
- галерея;
- JSON.

Не делал отдельный экран «все товары»: история запусков уже отвечает на вопрос «что парсили».

### 6.2. Polling вместо WebSocket

Задача не требует мгновенных обновлений. `setInterval` раз в 1.5 секунды проще, чем WebSocket/SSE, и не требует соединения.

Когда статус становится `success/failed`, страница перезагружается.

### 6.3. Прогрессивное улучшение

Форма имеет `action="/runs"` и `method="post"`. Если JS отключён, она всё равно создаст запуск и сделает redirect. JS перехватывает submit только для более удобного JSON-запроса и сообщений об ошибках.

Это дешёвая страховка, но она требует `python-multipart` — добавил.

### 6.4. Тёмная тема

Локальный инструмент, но хотелось, чтобы им было приятно пользоваться. CSS без внешних CDN и шрифтов: приложение должно работать офлайн.

## 7. Docker и PostgreSQL: что проверялось

### 7.1. Docker daemon

Первый факт:

```text
failed to connect to the docker API at unix:///Users/igor/.docker/run/docker.sock
```

Docker Desktop был установлен, но не запущен. Запустил `open -a Docker`, дождался daemon.

**Урок:** «Docker установлен» ≠ «Docker работает». Проверять daemon до написания compose.

### 7.2. Сборка образа и sandbox

Сборка упала:

```text
failed to update builder last activity time:
open /Users/igor/.docker/buildx/activity/.tmp-...: operation not permitted
```

Причина — sandbox не даёт писать в `~/.docker/buildx`. Это ограничение окружения, а не проекта.

Решение для проверки:

```bash
DOCKER_CONFIG=$PWD/.docker-config \
DOCKER_HOST=unix:///Users/igor/.docker/run/docker.sock \
docker compose build web
```

С `DOCKER_CONFIG` пришлось симлинкнуть `cli-plugins`, иначе `docker compose` не находился. В обычном терминале пользователя это не нужно.

**Урок:** ошибки Docker в агенте могут быть про sandbox, а не про Dockerfile. Не менять Dockerfile, пока не понял, какой слой упал.

### 7.3. Образ собрался

Проверено:

- `pip install .` внутри `python:3.13-slim`;
- `uvicorn app.main:app` стартует;
- `/health` отвечает `{"status":"ok","database":"ok"}`;
- статика и шаблоны доступны;
- история из PostgreSQL видна.

### 7.4. CDP из контейнера не работает

Создал запуск `source=cdp` через контейнер:

```text
Режим browser требует Playwright...
```

Причина: Dockerfile ставит только основные зависимости, без `.[browser]`. Даже если поставить Playwright, Chrome на хосте слушает `127.0.0.1`, и `host.docker.internal` до него не достучится.

Решение: **не** тащить Chromium в образ и не расширять CDP на `0.0.0.0`. Вместо этого:

- README говорит: для CDP запускай приложение локально;
- сообщение об ошибке объясняет, что в Docker браузерный режим не включён;
- compose остаётся для истории/API/HTML.

**Урок:** архитектурное ограничение лучше явно задокументировать, чем имитировать поддержку.

## 9. Ошибки и исправления

### 9.1. Таблица не влезала по ширине

Первый скриншот показал, что колонка «Открыть» обрезается: 9 колонок не помещались в 1180 px.

Исправил: объединил «Рейтинг» и «Отзывы» в одну ячейку, убрал лишнюю колонку. Проверил скриншотом, а не на глаз.

**Урок:** верстку проверяй рендером, а не только по HTML.

### 9.2. «Наличие» показывало schema.org URL

В детальной странице было:

```text
Наличие: https://schema.org/InStock
```

Это техническая правда, но плохой UI. Заменил на «В наличии / Нет в наличии / —».

**Урок:** сырые данные не всегда стоит показывать как есть, даже если они корректны.

### 9.3. Наивные timestamp'ы в SQLite

SQLite теряет timezone у `DateTime(timezone=True)`, и API отдавал время без `Z`. В Postgres было с timezone.

Исправил в сериализаторе: если `tzinfo` нет, считаем UTC и добавляем его. Теперь API консистентен.

**Урок:** тестовая БД может отличаться от продовой не только SQL, но и типами/временем. Нормализуй на границе.

### 9.4. Docker-образ без Playwright

Первый `source=cdp` в контейнере дал ошибку с советом `uv sync`, которого в контейнере нет.

Исправил сообщение: объяснил, что в Docker браузерный режим не включён, и что для CDP нужно локальное приложение. README синхронизирован.

**Урок:** сообщение об ошибке должно учитывать контекст запуска.

### 9.5. Неиспользуемый `request`

В form-route остался `request`, который не использовался. Убрал. Мелочь, но такие вещи накапливаются.

### 9.6. Docker build и sandbox

Потратил время на ошибку buildx, которая оказалась ограничением окружения. Решил через `DOCKER_CONFIG`/`DOCKER_HOST`, не меняя проект.

**Урок:** сначала определить, что именно упало — Dockerfile, daemon, buildx или sandbox.

## 10. Принципы, которые помогли

### 10.1. Сначала границы, потом код

Я потратил время на вопрос «где живёт приложение и где Chrome», и это определило всё остальное. Если бы начал с кода, мог бы сделать красивый Docker-стек, который не умеет главного — CDP.

### 10.2. Один процесс — это фича, а не стыд

BackgroundTasks + lock + БД-статусы достаточно для локального инструмента. Celery выглядел бы «взрослее», но добавил бы Redis, worker и сложность без текущей потребности.

### 10.3. Денормализация ради UX

Колонки `name/sku/price/rating` дублируют JSON. Это нормально, потому что история и фильтры — главный сценарий. Полный JSON остаётся источником истины.

### 10.4. Тесты — офлайн, интеграция — отдельно

25 тестов не ходят в Ozon и работают за 0.1 секунды. Живой Ozon, Docker и CDP проверяются отдельными экспериментами. Это даёт быстрый цикл и не делает тесты хрупкими.

### 10.5. Мок внешнего мира, реальная БД

В тестах парсер замокан, но API, БД, шаблоны и фоновая задача настоящие. Это хороший баланс: быстро и всё равно проверяет интеграцию слоёв.

### 10.6. UI проверяй браузером

Скриншоты и Playwright-сценарий поймали то, чего не видно в HTML: обрезанную таблицу, кривой layout, работу polling.

### 10.7. Ограничения — часть результата

«Docker не умеет CDP» — не баг, а архитектурное следствие. Это записано в README, STATUS и сообщении об ошибке. Пользователь не должен выяснять это сам.

## 11. Что бы я сделал иначе

- **Раньше проверил бы Docker daemon и сборку**, до написания всего приложения. Это сэкономило бы нервы.
- **Сразу бы сделал скриншот дашборда** после первой версии, а не после реализации — таблица не влезла бы раньше.
- **Подумал бы про Alembic** на старте. `create_all` быстрее, но миграции всё равно понадобятся.
- **Добавил бы загрузку JSON в UI** — это естественный fallback, когда браузерный режим недоступен. Сейчас есть только CLI `--json`.
- **Сразу бы вынес `build_options`** в отдельную функцию, а не дублировал бы логику между API и формой. (В итоге так и сделал, но не с первого раза.)
- **Проверил бы `python-multipart`** до написания form-route; без него форма падает.

## 12. Чек-лист для похожего веб-приложения

1. **Определи границы:** что живёт в браузере, что в контейнере, что на хосте.
2. **Проверь инфраструктуру до кода:** Docker daemon, БД, порты.
3. **Выбери минимальный UI-стек:** Jinja2 хватает чаще, чем кажется.
4. **Сделай статусную модель:** `queued/running/success/failed` — минимум для фоновых задач.
5. **Коммить `running` до долгой операции**, иначе UI врёт.
6. **Отдельная сессия в фоновой задаче.**
7. **Сериализуй внешние вызовы** (lock/очередь), если сайт не любит параллельность.
8. **Храни и JSON, и денормализованные поля** для истории.
9. **Нормализуй время на границе API.**
10. **Пиши офлайн-тесты с моком внешнего сервиса.**
11. **Проверяй UI скриншотом/Playwright, а не только HTML.**
12. **Документируй ограничения** в README, STATUS и текстах ошибок.

## 14. Главная мысль

Самое важное решение было не «FastAPI или Flask» и не «React или Jinja2», а **разделение ответственности между хостом и контейнером**.

Если сформулировать коротко:

> Сначала найди, где уже работает то, что ты не можешь воспроизвести в коде (браузер, CDP, сессия), и построй приложение вокруг этого места, а не против него.

И второе:

> Для локального инструмента простота важнее «взрослой» архитектуры. BackgroundTasks + lock + PostgreSQL + polling — это достаточно, пока задача не требует большего.
