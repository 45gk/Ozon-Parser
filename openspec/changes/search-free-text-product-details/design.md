# Design

## Context

См. `proposal.md` — Why. Текущий поиск (`app/services/search_runner.py`) получает
`OzonSearchResult` из `ozon_parser.search.fetch_search_browser`, где браузерная
сессия уже авторизована и прошла антибот-проверку. `SearchItem` хранит только
поля плитки. В проекте нет Alembic: схема создаётся через
`Base.metadata.create_all`, поэтому добавлять колонки в существующие таблицы
нельзя без ручной миграции.

## Goals / Non-Goals

**Goals:**

- Один вход для ссылки и свободного текста без ломки `POST /api/searches`.
- Разбор карточек внутри уже открытой браузерной сессии, без N новых запусков
  Chrome и без засорения истории `parse_runs`.
- Partial success: ошибка карточки видна, но не отменяет выдачу.
- Совместимость с существующей PostgreSQL-базой без ручных `ALTER TABLE`.

**Non-Goals:**

- Глобальный каталог товаров и дедупликация между поисками.
- Фоновая очередь, retry и прогресс по каждой карточке.
- Разбор карточек для уже сохранённых поисков задним числом.
- Изменение CLI и одиночного парсинга карточек.

## Decisions

### 1. Свободный текст нормализуется в `/search/?text=...`

`SearchCreate.url` остаётся единственным обязательным полем. Валидатор
различает URL и текст:

- значение с `http(s)://` или `www.` считается ссылкой и проверяется как
  `/category/...` или `/search/...`;
- остальное считается поисковой фразой; пробелы схлопываются, строится
  `https://www.ozon.ru/search/?text=<quote_plus>`.

Альтернатива — новое поле `query` — отклонена: она ломает существующий API и
заставляет UI выбирать поле. Нормализация сохраняет один контракт и один
`search_url`.

Ссылка на `/product/...` не превращается в текстовый запрос: это явная ошибка
пользователя, а не название товара.

### 2. Карточки разбираются в той же браузерной сессии

`fetch_search_browser(..., include_products=True)` после получения списка
вызывает `entrypoint-api` для каждой позиции через `_fetch_api_in_page` на той
же странице. Это переиспользует cookies и уже пройденный challenge.

Альтернативы:

- отдельный `fetch_product_browser` на каждую позицию — надёжно, но открывает
  N браузеров/контекстов и резко замедляет поиск;
- прямой HTTP-клиент — не проходит антибот Ozon;
- отдельные `ParseRun` — засоряют историю одиночных парсингов и требуют
  фоновых задач.

Challenge при запросе карточки обрабатывается один раз. Если он не пройден,
ошибка блокировки назначается текущей и оставшимся позициям, чтобы не ждать
таймаут N раз.

### 3. Подробности хранятся в новой таблице `search_item_products`

Одна запись на `SearchItem` (unique FK, cascade delete) с денормализованными
полями и полным JSON. Новая таблица создаётся `create_all` и не требует
изменения `search_items` или `search_runs`.

Почему не колонки в `search_items`: `create_all` не делает `ALTER TABLE`, а
Alembic в проекте нет. Почему не `parse_runs`: это отдельная сущность истории
одиночных запусков; поиск должен хранить снимок карточки, даже если одиночный
парсинг не запускался.

### 4. Ошибки карточек не меняют статус поиска

`SearchRun.status = success`, если получена выдача. Для каждой позиции
сохраняется `status` (`success` / `failed`) и `error`. UI показывает счётчик
разобранных и ошибки в раскрывающемся блоке.

### 5. Флаг `parse_products` по умолчанию включён

Новое поведение должно работать без дополнительных действий. Флаг нужен для
быстрых запусков и тестов; он сохраняется в `options`, поэтому кнопка
«Повторить» воспроизводит режим.

## Risks / Trade-offs

- [100 карточек = 100 последовательных API-запросов] → ограничение `limit`
  остаётся 1–100, запросы идут последовательно; UI предупреждает о времени.
- [Challenge в середине разбора] → обрабатывается один раз, затем оставшиеся
  позиции получают ошибку блокировки.
- [Нет Alembic] → новая таблица создаётся автоматически; для будущих изменений
  колонок миграция всё ещё нужна.
- [Дублирование данных между поисками] → осознанный снимок выдачи; дедупликация
  не входит в задачу.
- [API-совместимость] → поле `url` обязательно, старые запросы работают;
  меняется только допустимый формат значения.

## Migration Plan

1. Задеплоить код; при старте `create_all` создаст `search_item_products`.
2. Старые поиски открываются как раньше: у позиций просто нет записи карточки.
3. Rollback: остановить приложение; новая таблица не влияет на старый код,
   при необходимости удалить `search_item_products`.
